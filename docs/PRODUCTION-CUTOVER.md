# Replacement production cutover

This runbook governs replacing the currently deployed Game Arena production experience with the exact release that passes staging certification and human UAT.

It does not authorize a cutover by itself.

## Entry criteria

Do not begin production execution until all of the following are true:

- the release is identified by a full Git SHA;
- the same SHA has a successful immutable image-publication record;
- the same SHA was deployed to staging and produced `READY FOR UAT`;
- the protected free and premium QA accounts passed;
- the signed Admin role matrix passed;
- the approved visual baseline matches or a reviewed update has been accepted;
- human UAT has an explicit non-sensitive approval reference;
- the owner explicitly authorizes production execution;
- production secrets/providers/domains/backups/monitoring are ready for the selected launch scope;
- a rollback owner is named and the current production deployment is still recoverable.

## Cutover rule

Promote the **same immutable SHA-tagged application artifacts** that were certified in staging. Do not rebuild application images for production and do not deploy a mutable `latest` tag.

Runtime configuration and secrets may differ by environment, but application artifact identity must remain unchanged.

## Pre-cutover record

Capture before changing traffic:

- release SHA and image digests;
- staging certification workflow/run and evidence artifact;
- human UAT reference;
- existing production endpoint and current rollback reference;
- replacement production endpoint before public traffic;
- database migration/version state and backup/restore point;
- production provider modes and readiness;
- named cutover and rollback owners.

No secret value belongs in this record.

## Execution order

1. Deploy the certified SHA to the replacement production environment without switching public traffic.
2. Run database migrations using the reviewed production migration procedure.
3. Verify player/API/game-origin health and private Admin access against the replacement environment.
4. Run the non-destructive production smoke suite. Do not create test payments, rewards, customer mutations or administrative writes during smoke.
5. Confirm observability, backup and rollback signals are healthy.
6. Switch the public domain/traffic to the replacement environment using the approved DNS/load-balancer mechanism.
7. Repeat the non-destructive smoke through the public production hostname.
8. Observe the new environment before decommissioning anything.

## Immediate smoke requirements

At minimum verify:

- public home and catalogue load over HTTPS;
- API health/readiness is healthy;
- deployed source SHA is the authorized SHA;
- controlled game-origin health is reachable;
- a representative public game/media asset is reachable;
- private Admin authentication boundary is intact;
- no new critical/high error burst is visible;
- no unexpected payment/reward/customer mutation was generated by smoke.

## Rollback triggers

Rollback or stop traffic expansion for any of the following:

- deployed artifact identity cannot be proven;
- player/API/game-origin becomes unavailable;
- authentication/session exposure or widespread failure;
- payment/entitlement inconsistency;
- unauthorized Admin access;
- database migration/durability issue;
- critical/high security finding;
- material latency/error regression against the staging baseline;
- owner or incident lead calls a stop.

## Rollback procedure

- stop further traffic changes;
- restore routing to the previous known-good production target when safe;
- do not blindly reverse an irreversible database migration;
- use the documented database restore/forward-fix procedure appropriate to the migration;
- record the failed SHA, symptoms and evidence;
- open/fix regression tests before attempting another promotion.

## Old production retirement

The old production environment is a rollback target during cutover. Do **not** delete it at the moment traffic switches.

Retire it only after:

- replacement production smoke passes;
- the agreed observation period completes without a rollback trigger;
- payment/entitlement and operational telemetry is reconciled for the launch scope;
- backup/restore evidence for the new environment is confirmed;
- the owner explicitly approves retirement.

Retirement should remove obsolete compute, DNS targets, credentials and unused storage according to the infrastructure runbook while retaining required audit/evidence records.

## Authority boundary

`.github/workflows/promote-production.yml` only proves that an exact SHA is eligible for production preparation after staging certification and UAT. It intentionally does not execute this runbook.

Production deployment, traffic cutover and retirement remain separate explicit owner-authorized actions.
