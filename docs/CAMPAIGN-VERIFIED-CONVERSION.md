# Verified campaign conversion increment (#196/#197)

Current server dispatch supports both direct JazzCash orchestrator and external Payment Service. This increment implements a short-lived hashed return receipt on the already captured direct JazzCash transaction; the endpoint returns only safe actual amount/currency/plan and transaction reference. Receipt does not authenticate a user, grant premium, or initiate a charge. Frontend no longer marks URL-only success as a purchase or changes entitlement from that URL; account service stays authoritative. GA4 purchase is emitted only for an authenticated/receipt-verified result, with actual amount, items and transaction_id. Existing analytics setting gates marketing events; operational backend funnel and an explicit landing consent experience are still pending. Existing browser dedupe remains best-effort; backend durable conversion outbox is still required for cross-device delivery and GA4 verification.

External Payment Service does not yet expose a verified correlated receipt here. Its return cannot emit purchase from query parameters; complete its authoritative payment projection once actual provider response/correlation contracts are confirmed. No invented provider fields.

Important pre-existing direct-flow risk discovered: callback link-intent, wallet and subscription maps are not included in normalized PostgreSQL descriptors; payment token seal is base64 encoding, NOT encryption. Do not simply add those maps to persistent storage. Implement encrypted token storage and durable idempotent charge reservation/reconciliation in a separate reviewed provider work package before claiming callback replay safety. This increment does not modify charge behavior or certify live payment. No production changes.
